## The failure matrix

The four failures the SOW names, with the behaviour the rail must show. #46 fills in the observed behaviour and evidence.

| Failure | Must happen | Must never happen |
| --- | --- | --- |
| **Sequence collision** (two payouts race for the same sequence number) | One payout lands and the other retries on a fresh sequence | A second transfer for the same submission |
| **Co-signer outage** | The payout stays pending, an alert fires, and it resumes when the co-signer returns | A payout with one signature, or a status that says "paid" |
| **Daily cap exceeded** | Both signers refuse independently and an alert fires | Either signer alone lifting the cap |
| **Horizon timeout** (outcome unknown) | The payout stays reconcilable and is resolved only from on-chain proof | A blind resubmit, which is exactly how a double payment happens |

## Mainnet: what must be true first

{% hint style="danger" %}
`COSIGNER_ISOLATION_LEVEL=same-workspace` refuses to sign on `STELLAR_NETWORK=public`. That is deliberate. #51 needs the co-signer moved to its **own account** (ADR-0001's exit criterion), and moving it is a deployment change with no service-code change.
{% endhint %}

1. The co-signer runs in a separate account: its own control plane, member list, CI and database credentials.
2. Fresh mainnet signer keys are generated **directly into the secrets store**, and all three are recorded *before* `set-options`.
3. No single service holds signer weight that reaches the threshold. The custody guard enforces this.
4. The #50 preflight passes without submitting anything.
5. A current, written approval names the exact destination and amount. It must be in by **Tue 29 Sep, end of day**.
6. If the outcome is unknown, it is investigated, **never retried blindly**.
